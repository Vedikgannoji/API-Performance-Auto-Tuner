# Phase 3 CLI and package review

Status: CLI foundation and control-session lifecycle implemented, ready for joint testing. No Phase 4 forwarding has been implemented or claimed.

## Available now

- `autotuner --help` and `--version`, plus `python -m autotuner`.
- `init`: create a validated observe-mode JSON configuration. Existing files require `--force`.
- `config check`: resolve and validate configuration without network activity.
- `doctor`: offline configuration/Python checks; `--connect` explicitly performs a bounded TCP upstream reachability check, not TLS or HTTP validation.
- `serve --check`: validate without opening a listener.
- `serve`: run a loopback control session with health/status endpoints and Uvicorn shutdown handling.
- `status`: query a running control session with a two-second timeout, proxy-environment bypass and no redirect following.

JSON responses have schema_version 1 and are emitted on stdout; diagnostics use stderr. Invalid configuration is reported by field location without printing rejected values. The precedence order is defaults, JSON file, AUTOTUNER_UPSTREAM/AUTOTUNER_LISTEN/AUTOTUNER_MODE, then explicit flags. AUTOTUNER_CONFIG selects the default file path; --config takes precedence. init always creates observe mode rather than inheriting an environment mode.

The control session reserves `/_autotuner/health` and `/_autotuner/status`. It reports forwarding_enabled=false and cache_serving_enabled=false even if adaptive mode is requested. Other HTTP requests receive 501 explaining the Phase 4 boundary. No upstream traffic is generated by serve, config check or offline doctor. Session state is in memory; persistent storage arrives in Phase 5.

Exit codes implemented here: 0 success or handled interruption; 1 runtime/connectivity/I/O/protocol failure; 2 invalid arguments, configuration, missing file or overwrite refusal. Code 3 is reserved for later benchmark/scenario assertion failures. Continuous serve --json is rejected; use serve --check --json or status --json instead.

## Joint test sequence

Run from the repository root, preferably in your development virtual environment:

```cmd
python -m pip install -e ".[test]"
autotuner --help
autotuner --version
autotuner init --config phase3.local.json
autotuner config check --config phase3.local.json --json
autotuner doctor --config phase3.local.json --json
autotuner serve --config phase3.local.json --check --json
python -m pytest tests/test_cli.py -o addopts=""
python -m pytest
```

Keep the example observe mode. In one terminal run `autotuner serve --config phase3.local.json`; in another run `autotuner status --config phase3.local.json --json`. Verify the session is running but forwarding and cache serving are false. Stop with Ctrl+C and verify status then exits with a runtime failure. The default product port is 8080; it does not replace the existing demo server on 8000. Optional `doctor --connect` contacts the configured upstream, so use it only with a backend you intend to probe.

If the console command is not on PATH, use the equivalent `python -m autotuner ...` commands in the same environment. Do not run init --force on a configuration you want to keep.

## Verification and limitations

Focused tests cover defaults, environment/flag precedence, overwrite protection, redaction, invalid input, offline behavior, explicit TCP diagnostics, mocked status responses, no redirect following, runner options, interruption and ASGI startup/shutdown. Wheel installation is checked outside the source directory using existing dependency packages and an isolated target directory. This is not a clean dependency download or cross-platform qualification.

The managed sandbox blocks TCP self-pipe setup, so local pytest uses scripts/test_socketless.py. Control-session HTTP behavior is tested in process and the Uvicorn invocation is mocked; a real foreground listener and Ctrl+C still need our normal-terminal review. Existing demo and JavaScript tests remain part of regression verification. No public package publication has occurred.

Later commands (endpoints, insights, cache controls, dashboard and reports) will be connected when their product services exist. The CLI does not expose stubs that claim to operate an unimplemented proxy. Phase 4 begins only after we test and review this foundation together.
